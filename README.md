# meridian-core

The runtime of [Open Meridian](https://open-meridian.com), the open-source
OEMS, in Rust. It is what runs in your own environment, beside your own
database: the message bus, the stores, the conductor, the dashboard people
sign in to, and one sidecar per plugin. Traders build their own tools on it
with AI agents, and developers write their bots and analytics against it.

## Start here

The documentation is at [open-meridian.dev](https://open-meridian.dev).
Install the command line, then follow [INSTALL.md](INSTALL.md), which walks
the whole path from registering a deployment on the platform to signing in:

```sh
curl -fsSL https://raw.githubusercontent.com/open-meridian/meridian-cli/main/install.sh | sh
meridian doctor
meridian up --id DEP-…            # with the enrolment code from open-meridian.com
meridian connect
```

A laptop cluster is enough to try it (Rancher Desktop, k3s, kind or Docker
Desktop). `meridian up` installs the chart,
`oci://ghcr.io/open-meridian/charts/meridian-runtime`;
[deploy/chart/README.md](deploy/chart/README.md) says what each of its values
does, for the files `meridian up -f` takes.

To write a plugin, `meridian plugin new` starts one from the Python SDK's
reference plugin ([meridian-python](https://github.com/open-meridian/meridian-python)).
On a deployment installed with `meridian up --development`, `meridian plugin
dev` runs it as you write it, each save running in about a second; the
plugin's `AGENTS.md` teaches any coding agent that loop. See
[meridian-cli](https://github.com/open-meridian/meridian-cli).

## What runs

- **dashboard** -- the one address a firm's staff use. It signs people in
  through the firm's directory (OpenID Connect or LDAP) or through accounts it
  holds itself, runs the first-run wizard, Settings (where a deployment admin
  authors accounts, groups and permissions and manages each plugin) and a
  lost-password reset with a code from the platform, and serves each plugin's
  page on its own name, `<instance>.plugins.<host>`, with the plugin UI kit
  ([meridian-ui](https://github.com/open-meridian/meridian-ui)) at
  `/.meridian/ui/<version>/` on every host. A browser's session is held in
  memory; a terminal's (`meridian connect`) in the database, so it survives a
  restart or an upgrade.
- **conductor** -- the only component holding the deployment's key, and so the
  only one that reaches the platform. It also holds the configuration store:
  accounts, who may reach what, and plugin settings, as a deployment admin
  authors them. There is one conductor; redundancy means a standby, not a
  second one.
- **instrument store** -- what this deployment knows about instruments, and the
  answer to every instrument question, locally. For identity it holds a copy of
  what the platform publishes, so a deployment keeps working through an outage
  of the platform it pulls from.
- **street store** -- what custodians say is held: statements, holdings,
  custodial positions. The one store whose contents nothing can rebuild.
- **sidecar** -- one per plugin, bound to loopback, holding that plugin's broker
  credential and enforcing its grants. A plugin reaches its sidecar and
  nothing else.
- **launcher** and **registry** -- the deployment's own catalogue of plugin
  versions, and what runs an approved one.
- **broker** -- NATS, carrying the bus, with permissions generated from the
  grants rather than written by hand.

Setting a deployment up also runs the **first-run** job, which holds the
narrow rights the wizard's answers need, and the **key** and **migrate** jobs.

The key is generated by the conductor and never leaves it; the platform holds
only its public half. A deployment holds one platform address, its own
identifier and its key, and knows nothing about the platform's shape, so the
platform can scale, move and be redirected without anything here changing.

## Releases

Every commit on `main` that passes CI is published: the image
`ghcr.io/open-meridian/meridian-runtime`, tagged by commit and `latest`, for
amd64 and arm64, and beside it the chart,
`oci://ghcr.io/open-meridian/charts/meridian-runtime`, versioned `0.1.<n>` and
naming that image. The image carries every binary -- street, instrument,
sidecar, conductor, dashboard, broker-config, first-run and launcher -- and the
plugin UI kit, built from meridian-ui at the commit the `Dockerfile` pins; the
dashboard answers a page asking for any kit `0.x` with the newest it carries.
Each binary reports the release it was built as, `0.1.<n>+<commit>`, compiled
in rather than configured, in its component report and as
`meridian-<binary> --version`; a build publish did not make says `-dev`.
A running deployment moves to a newer chart with `meridian upgrade-deployment`,
or from a firm's own pipeline.

## Working on it

    make ci-local

Local green is the completion signal, and `make install-hooks` runs it before
every push. `docker compose up` runs every component locally with a database
and a broker. `make demo` proves the round trip against a platform -- resolve,
miss, pull, apply, then take the platform away and watch resolution keep
working -- and needs a checkout of the platform beside this one, which is not
public. [CLAUDE.md](CLAUDE.md) holds the rules that govern changes here.

## Layout

| Crate | What it is |
|---|---|
| `bus` | Topic routing and request-reply over a backend trait |
| `sidecar` | The gRPC surface a plugin binds to |
| `instrument` | The instrument store: resolve and apply |
| `street` | The street store: statements, holdings, custodial positions |
| `conductor` | The platform connection, the key, and outward reporting |
| `config` | The configuration store: accounts, access, settings |
| `access` | Evaluating who may reach what, shared by the conductor and the dashboard |
| `dashboard` | The pages people sign in to, Settings, the plugins' pages and the kit |
| `first-run` | What a deployment's wizard decides, and the narrow rights that write it |
| `symbology` | The identifier fallback order, shared by two components |
| `domain` | The domain messages, generated from `proto/` by `make codegen` |
| `runtime` | Every binary, and what wires each process together |

`proto/` holds the domain messages -- holdings, reference data, accounts -- that
the runtime carries past its sidecar. A plugin never sees them: its surface is
the sidecar's, in [meridian-schema](https://github.com/open-meridian/meridian-schema).
They are contract-tier here, so a commit changing one names a queued task in a
`Contract-Revision:` trailer.
