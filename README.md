# meridian-core

The Meridian deployment runtime, in Rust: message bus, sidecar, kernel,
reference replica and dashboard. This is what ships to a client and runs in
their own infrastructure, beside their own database.

See [CLAUDE.md](CLAUDE.md) for the rules that govern changes here.

    make ci-local

## Running a replica

The replica holds a copy of the security master and answers instrument questions
locally, so a deployment keeps working through an outage of the platform it
pulls from.

The published image is `ghcr.io/open-meridian/meridian-replica`, tagged by
commit and as `latest`.

Bringing one up is three steps and no more. The private key is generated by the
replica and never leaves it; the platform holds only the public half, and has
nowhere to put a private one.

```bash
# 1. Generate a key, and print the public half.
docker run --rm -v meridian-keys:/var/lib/meridian \
  ghcr.io/open-meridian/meridian-replica public-key

# 2. Register that public half with the platform. You get back a deployment id.

# 3. Run it.
docker run -d -v meridian-keys:/var/lib/meridian \
  -e MERIDIAN_DEPLOYMENT_ID=DEP-... \
  -e MERIDIAN_PLATFORM_ADDRESS=https://open-meridian.com \
  -e MERIDIAN_DATABASE_URL=postgres://... \
  ghcr.io/open-meridian/meridian-replica
```

Nothing else is configured, and that is deliberate. A deployment holds one
address, its own identifier and its key, and knows nothing about the platform's
shape, so the platform can scale, move and be redirected without anything here
changing or restarting.

`docker compose up` runs the same thing with a database alongside it, and
`make demo` proves the whole round trip against a platform: resolve, miss, pull,
apply, then take the platform away and watch resolution keep working.

## Layout

| Crate | What it is |
|---|---|
| `bus` | Topic routing and request-reply over a backend trait |
| `sidecar` | The gRPC surface a plugin binds to |
| `reference` | The replica: resolve, pull, escalate, apply |
| `replica` | The process that runs one |
