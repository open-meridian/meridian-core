# Jobs that CI runs and `make ci-local` cannot.
#
# Format: job-id<TAB>reason. A bare job id is rejected; the reason is the point.
# Every entry here is a hole in "green locally means green in CI", so each one
# has to be worth the hole.
#
# The bar: a job belongs here only when reproducing it locally is impossible
# rather than merely inconvenient. Needing a credential, a hosted service, or a
# model is impossible. Being slow is not.

claude-review	Runs the review passes in REVIEW.md against the diff by invoking a model. Not reproducible locally: it needs credentials and produces a judgement, not a verdict. Advisory only -- ci-local is the required status check, this is not.
claude	The on-demand responder, triggered by an @claude mention on an issue or a review comment. Runs no checks and gates nothing; it exists so a human can ask for work in a thread. Nothing local corresponds to a mention.
publish	Promotes the release candidate -- the runtime and analytics images, amd64 and arm64, that ci built and tested for the merged tree and tagged tested-<tree> once green (ruling 1071) -- tagging it with the commit and latest, without a rebuild. Not reproducible locally by design: it needs a registry credential, and a local target that pushed would mean every developer could publish from a laptop. It gates nothing; it runs on the merge to main and refuses a tree no green ci run tested, so nothing is published that the gates have not seen.
close	Thanks a pull request from outside the organisation, points it to issues and closes it (outside-pull-requests.yaml). Not reproducible locally by design: it acts on who opened a pull request and on GitHub's own view of whether they are inside this organisation, neither of which exists on a laptop. It checks nothing and gates nothing.
harness	Pushes the plugin harness image, files only, beside the runtime image of the same commit (kernel/the-plugin-harness-is-its-own-image). Not reproducible locally for the same reason as `publish`: it needs a registry credential, and a local target that pushed would mean anybody could publish from a laptop. What it pushes is built and checked locally by `make harness-check`, which ci-local runs: the same Dockerfile stage, copied out, its files listed, scanned for a fixed password, and run with three plugins. It gates nothing, and runs only after `publish` has put that commit's runtime image in the registry.
chart	Packages the Helm chart and pushes it beside the image it names. Not reproducible locally for the same reason as `publish`: it needs a registry credential, and a local target that pushed would mean anybody could publish a chart from a laptop. It gates nothing, and runs only after `publish` has put the image it pins in the registry.
backup-image	Pushes the backup image the chart's backup CronJob runs in (pg_dump and age; kernel/a-deployment-is-backed-up-and-restored) beside the runtime image of the same commit. Not reproducible locally for the same reason as `publish`: it needs a registry credential, and a local target that pushed would mean anybody could publish from a laptop. What it builds is built locally by `make e2e-cluster-backup`, and it runs only after `publish`.
postgres-image	Pushes the brought database's image under Patroni (deploy/database: postgres:16-alpine's server, Patroni and pgBackRest; step 3b) beside the runtime image of the same commit, which the chart pins. Not reproducible locally for the same reason as `publish` and `backup-image`: it needs a registry credential. What it builds is built locally by `make e2e-cluster-failover` in the HA profiles (`make e2e-cluster-scaled`), and it runs only after `publish`.
e2e-cluster-k3d	Installs the chart on a throwaway k3d cluster, against the real platform, and signs a person in: paths 1 and 2 of spec/installation-and-first-run and path 1's other two ways in, and an upgrade in place from the chart published last. Reproducible locally and exactly, as `make e2e-cluster-k3d E2E_CLUSTER_TARGET=<one of the five>`, but not from ci-local: it needs k3d and a checkout of meridian-platform, which is private and is read with a GitHub App token, and ci-local assumes neither. It gates the merge, and so publication: it runs on every pull request alongside ci-local (ruling 1066), each target a required check, and publish runs only on the merge.
licence	Asks anyone outside the organisation who writes on an issue to agree, once, to the suggestion licence (licence.yaml, the action in .github/actions/licence-check). Not reproducible locally by design: it acts on GitHub's issue events and on GitHub's view of who is inside the organisation, neither of which exists on a laptop. Its decisions are tested locally by `make licence-check-test`, which ci-local runs. It checks nothing and gates nothing.
footprint-judge	Judges the desktop footprint's peak memory by the median of the e2e-cluster jobs' peaks (step 3b, ruling 1058). Reproducible locally as `make footprint-judge FOOTPRINT_PEAKS=<files>`, but not from ci-local: it needs the peaks the e2e-cluster-k3d jobs measured, which ci-local never runs.
cargo-cache	Keeps the release build's cargo caches in main's cache scope on every merge, so a new pull request's images job reads current ones (actions/cache scopes a pull request's caches to that pull request, and ci does not run on main). Not reproducible locally by design: it acts on GitHub's cache service, which a laptop has no part in; a laptop's BuildKit keeps its own cargo caches. It builds the runtime image as runtime-image does, which ci-local's images stage runs, and checks and gates nothing.
e2e-cluster-arm64	Builds the release candidate's arm64 images on GitHub's arm64 runner, pushes them by digest, and installs the chart on a k3d cluster there, as e2e-cluster-k3d does on amd64 (ruling 1071). Reproducible locally on an arm64 machine as `make runtime-image analytics-image` and `make e2e-cluster-k3d E2E_CLUSTER_TARGET=e2e-cluster`, but not from ci-local: it needs k3d, the private meridian-platform and a registry credential to push. A required check.
release-candidate	Tags the images every check of a green ci run tested as tested-<tree>, the candidate publish promotes (ruling 1071). Not reproducible locally by design: it needs a registry credential, and runs only once the run's checks are green. Builds nothing and checks nothing.
claims-check	Holds every measurement the run's cluster jobs made, and every class the claims ledger holds, to their bounds (366; ruling 1113). It reads the k3d jobs' claims files, which only those jobs make: the local gate skips k3d. Reproducible locally as `make claims-check CLAIMS_RUN=<files>` on kept runs, and the gate runs `make claims-check` on the ledger alone.
failover-images	Builds the runtime and analytics images once for failover-repeat's runs (failover-repeat.yaml, by hand only), as runtime-image and analytics-image build them, over the release build's cargo caches main keeps. Reproducible locally as `make runtime-image analytics-image`, but not from ci-local: it only feeds the repeated cluster runs below, which ci-local never runs. Checks nothing and gates nothing.
failover-repeat	Runs e2e-cluster-failover in each profile named several times over (one matrix of profiles x runs, ruled 2026-11-11), each on its own runner and k3d cluster (accepted 2026-11-07: the five local runs a step 3b change was proved by, moved to CI). Reproducible locally as `make e2e-cluster-k3d E2E_CLUSTER_TARGET=e2e-cluster-failover PROFILE=<profile>`, run that many times, but not from ci-local: it needs k3d and, in ha, three agents. By hand only; gates no merge.
failover-verdict	Green only when every failover-repeat run and the images they ran were. Reads the jobs' results, which exist only on GitHub; runs no check of its own.
tier	Plans the run's tier (tools/ci_tier.py plan): every job on the merge queue, the fast tier and what its paths select on a pull request. It runs no check of its own; what it decides is held by `make ci-tier-check` in ci-local's checks stage, and ci-local fails a queue run where any job did not succeed.
e2e-harness-left	Reports, under its own name, a required e2e-harness group the pull request's tier leaves to the merge queue, so the pull request can be queued; it runs nothing and says so. Never runs on the merge queue, whose plan leaves nothing (tools/ci_tier.py, held by `make ci-tier-check`).
e2e-cluster-left	Reports, under its own name, a required cluster run the pull request's tier leaves to the merge queue, as e2e-harness-left; never on the merge queue.
